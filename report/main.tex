\begin{abstract}
\noindent
Large-language-model (LLM)-integrated writing assistants run as browser extensions that
silently observe the text a user types or pastes into web-page fields and send it to their
servers for analysis. We measure how much of a confidential document such tools transmit \emph{by
default}---even when the user has been told not to share it with any AI tool---using an
HTTPS man-in-the-middle proxy and a synthetic memo carrying twelve unique planted
identifiers, including a UUID canary. Across five runs each, Grammarly and LanguageTool
transmitted essentially the entire document (\textbf{99.0\%} and \textbf{91.9\%} of
characters) and \textbf{all twelve secrets, including the canary}, while a no-extension
baseline transmitted nothing. Extending the measurement to the host operating system
shows the exposure is \emph{surface-dependent}: merely \emph{opening} the file in
Microsoft~Word---with no paste and no submission---streams \textbf{96.8\%} of it to
Microsoft's default-enabled Office~AI cloud, and disabling a single Office setting stops
it entirely. Content leaves the machine whenever it enters an LLM-integrated surface,
independent of where the file is stored; we frame this as a gap between default behaviour
and reasonable user expectation rather than an exploit. All test data is synthetic and the
methodology is reproducible.
\end{abstract}

\begin{IEEEkeywords}
Browser extensions, data exposure, HTTPS interception, LLM-integrated productivity tools,
PII leakage
\end{IEEEkeywords}

\section{Introduction}

Large-language-model (LLM) integrated productivity tools (grammar checkers,
paraphrasers, and ``AI assistant'' extensions) have become a default part of many
users' browsers. They work by observing the content of text fields and sending that
content to remote servers for analysis, then returning suggestions. The convenience is
real; the privacy cost is largely invisible. A user who has been handed a confidential
file and told ``do not share this with any AI tool'' would not knowingly paste it into
a chatbot. But that same user may have a grammar-checking extension enabled in the
background, silently watching every field they type or paste into. The question this
project asks is deliberately mundane:

\begin{quote}
\emph{How does user data exposure differ across LLM-integrated productivity tools
during controlled use?}
\end{quote}

Concretely: when a confidential document is pasted into an ordinary text field with a
writing-assistant extension running by default, how much of that document leaves the
machine, and does it include the specifically sensitive parts?

This is not a search for a vulnerability. The tools examined here are doing exactly
what they were designed to do. Our contribution is a reproducible
\emph{measurement} of this default behaviour and an analysis of how it diverges from
users' expectations. Our contributions are:

\begin{itemize}[nosep]
  \item A measurement method that intercepts HTTPS traffic and searches it for planted
        secrets, including a unique UUID, to see how much of a document reaches a tool's
        servers.
  \item Measurements of two common grammar extensions (Grammarly and LanguageTool)
        against a no-extension baseline.
  \item A split into two kinds of tool---those that send text automatically in the
        background and those that send only on an explicit action---which explains why
        some AI writing tools leak and others do not.
  \item The same test applied to the host operating system, showing the leak depends on
        the surface: the document is sent by a desktop tool (DeepL), an invoked assistant
        (Edge~Copilot), or simply opening it in Word, but not by a USB, an iCloud sync,
        or a non-AI viewer.
  \item A check that turning off one Office setting stops the Word leak; which
        permissions the tools hold (all-sites text access, not microphone or camera); and
        that a tool declining to \emph{show} a secret does not mean it was not
        \emph{sent}.
  \item A list of the tools we tried and dropped, including a fake extension copying a
        well-known one.
\end{itemize}

\section{Background and Threat Model}
\label{sec:threat}

\paragraph{How these tools work.} A writing-assistant extension registers content
scripts that attach to editable elements (\texttt{<textarea>} and
\texttt{[contenteditable]}) on visited pages. When text appears in such a field, the
extension transmits it, typically over HTTPS or a WebSocket, to its backend,
which runs the analysis and returns suggestions. Because the analysis is server-side,
the text itself must leave the user's machine for the feature to function at all.

\paragraph{Threat model.} We model an ordinary, non-adversarial situation:

\begin{quote}
A user receives a confidential file and is explicitly told not to share it with AI
tools. They have a writing-assistant extension installed and enabled, the default
state for millions of users. In the course of normal work they paste part of the
document into a normal text field (an email reply, a web form, a notes box). Without
any further action, the extension transmits the content to its servers.
\end{quote}

The adversary here is not a criminal; it is the gap between the tool's default
behaviour and the user's mental model. The user believes they have withheld the
document from AI tools. In fact, merely pasting it into a field an unrelated extension
happens to watch has already transmitted it. Our measurement targets precisely this
gap: exposure that occurs with \emph{no user action beyond pasting}. The browser paste
is our primary scenario; we later broaden the same question to desktop applications and
to the act of merely \emph{opening} a received file (Section~\ref{sec:action-spectrum}),
where in some cases even the paste is unnecessary.

\section{Related Work}
\label{sec:related}

The privacy risks of browser extensions have been studied for the better part of a
decade. \citet{starov2017extended} were among the first to systematically measure the
``privacy diffusion'' enabled by extensions, showing that many leak identifying
information far beyond what their function requires. \citet{weissbacher2017exray}
built Ex-Ray to detect history-leaking extensions, and \citet{aggarwal2018ispy}
analysed and detected ``spying'' extensions that exfiltrate browsing behaviour.
\citet{chen2018mystique} scaled dynamic taint tracking to 181{,}683 extensions,
flagging thousands that leak privacy-sensitive information. These works established
that extension data collection is widespread and frequently undisclosed. They also
introduced the complementary detection methods the field still relies on: differential
string search, content-agnostic network analysis, and taint tracking. Static data-flow
analysis (e.g.\ DoubleX~\citep{fass2021doublex}) later added scale on the code side. This line of work rests on a longer study of the extension
security model itself: \citet{carlini2012chrome} evaluated Chrome's permission and
isolation architecture and showed that over-broad host permissions undercut its
guarantees, and \citet{pantelaios2020changed} showed that benign extensions can turn
malicious through later updates, which is why a runtime, network-level measurement of
what a tool \emph{actually} transmits is more reliable than trusting a single reviewed
snapshot.

More recent large-scale studies have moved from browsing metadata to \emph{page
content}. \citet{nayak2024experimental} experimentally analysed sensitive-data access
by extensions, including access to credentials on login pages, across the Chrome Web
Store. \citet{xie2024arcanum} built Arcanum, a dynamic taint-tracking system, and
found that thousands of extensions, used by an estimated 144 million people, collect sensitive on-page content such as email bodies, social-media activity, and
banking information, often without accurate disclosure. Closer to our own design,
\citet{bui2023extpriva} intercepted the network traffic of roughly 47{,}000 extensions
and compared the observed outbound data flows against each extension's stated privacy
practices, finding hundreds whose transmissions contradicted their disclosures. From the
tracking side, \citet{dambra2022sally} measured web tracking from the user's perspective,
building on the browser-instrumentation measurement paradigm established by OpenWPM
\citep{englehardt2016openwpm}.

The most behaviourally similar precedent is ``read-before-submit'' exfiltration:
\citet{senol2022leakyforms} showed that email addresses and even passwords are sent to
third parties \emph{as the user types}, before any form is submitted---a pattern recently
generalised by \citet{munir2025keystroke}, who found widespread third-party keystroke
event-listener interception across popular sites---and
\citet{starov2016contactforms} earlier quantified PII leaking from website contact forms.
We extend that ``transmitted before the user acts'' framing from trackers to
writing-assistant extensions. Methodologically, our detection step, searching
intercepted flows for known sensitive strings, follows a mature network-level
PII-measurement lineage rooted in dynamic taint tracking
(TaintDroid~\citep{enck2010taintdroid}) and network-level flow analysis over decrypted
mobile traffic (ReCon~\citep{ren2016recon}). Because outbound payloads can be encoded or
obfuscated, we adopt unique planted canaries in the spirit of the black-box
\emph{differential} leak detection introduced by AGRIGENTO~\citep{continella2017agrigento},
so that any transmitted fragment is unambiguously attributable to our input.

Closest to the present work, \citet{vekaria2025bighelp} audited nine generative-AI
browser assistants and, using traffic decryption, showed that several forward full
webpage content, including medical and banking details, to their own servers and
to third-party trackers. Our study is narrower and complementary: rather than a
broad crawl, we perform a deep, controlled, and \emph{fully reproducible} measurement
of a specific, common threat model (a confidential document pasted into a field with a
grammar checker running by default), using a planted-canary methodology that makes
each leak individually and unambiguously attributable. Where prior large-scale work
answers ``how many extensions leak,'' we answer ``exactly how much of a specific
confidential document leaves, and which sensitive tokens, for two representative
tools, with what reproducibility.'' In short, ours is the writing-assistant,
canary-proven complement to \citeauthor{vekaria2025bighelp}'s assistant-focused audit:
the same interception principle, narrowed to a single reproducible threat model and
strengthened with unique planted tokens so that every individual leak is provable, not
merely observed in aggregate.

Finally, why the transmitted \emph{content} matters is reinforced by a parallel line
of work on the privacy risks of large language models, which increasingly sit behind
these assistants. \citet{carlini2021extracting} showed that language models memorise and
can regurgitate verbatim personal data from their training set, and
\citet{nasr2025scalable} extended such extraction to aligned, production models,
recovering training examples from deployed systems such as ChatGPT;
\citet{lukas2023pii} quantified PII leakage from language models and showed that scrubbing
and differential privacy leave residual exposure. \citet{staab2024beyond} showed that
models can \emph{infer} sensitive attributes (location, age, income) from ordinary prose;
and \citet{mireshghallah2024cansecret} showed that LLM-integrated applications routinely
disclose information to contextually inappropriate recipients. Text sent to a writing
assistant is therefore not inert once it leaves the machine, which is precisely what
makes quantifying how much of it leaves, and to whom, worthwhile. This gap between what
users believe about their exposure and what actually leaves their devices has itself
become a subject of study: recent work frames a ``privacy paradox'' between user
perceptions and the reality of PII leakage in LLM-integrated
settings~\citep{privacyparadox2026}, motivating the concrete, quantified measurement we
provide here.

Threat-intelligence and industry reporting reinforce the downstream stakes of that
exposure. Deployed AI pipelines and unauthorised model-reseller/proxy services have been
observed silently saving and relaying users' inputs (including names, contact
details, and corporate data across many languages) without their knowledge or
consent~\citep{anthropic2026threats}, so text that leaves the machine can be retained and
reused well beyond the tool the user intended. Industry analyses report the same pattern
for the class of tools we study: a Unit~42 investigation of high-risk generative-AI
browser extensions found products marketed as productivity aids that read users' email as
it is composed and intercept prompts and page content~\citep{unit42genai2026}, while
enterprise-security reporting notes that such extensions read page content largely
invisibly to conventional data-loss-prevention controls, and that much of the data
entered into AI tools originates from personal, unmonitored accounts~\citep{csa2026extensions,
cyberhaven2026}.

\paragraph{Research gap.} Prior work either counts \emph{how many} extensions leak at
scale or audits AI assistants broadly; what is missing is a controlled, canary-proven,
per-secret measurement of how much of a \emph{single confidential document} leaves the
machine, across both the browser extensions and the everyday host applications (Office,
desktop clients, cloud-AI viewers) a real user actually encounters. This paper fills that
gap.

\section{Methodology}
\label{sec:method}

\subsection{Study design and conditions}

We measure three conditions: two writing-assistant extensions and a control.

\begin{itemize}[nosep]
  \item \textbf{Grammarly}: the archetypal always-on grammar/style checker and the
        motivating example for this project.
  \item \textbf{LanguageTool}: an independent grammar checker from a different
        vendor (LanguageTooler GmbH) that requires no account, making it the cleanest
        possible replication partner.
  \item \textbf{Baseline}: the identical browser and procedure with \emph{no}
        extension installed, to capture and subtract ordinary browser background
        traffic.
\end{itemize}

Two independent tools exhibiting the same behaviour constitutes within-class
replication, which is substantially stronger evidence than a single data point. The
scope was reached by evaluating and excluding several other candidates
(Section~\ref{sec:limitations}); the final design measures \emph{automatic /
background} exposure by grammar checkers.

\subsection{Test document and planted secrets}

The input is a synthetic ``confidential memo'' (2{,}065 characters, 245 words) written
to look like an internal compliance document and explicitly marked
``\textsc{do not forward}.'' Embedded in its prose are \textbf{twelve unique,
fictional identifiers}: names, an email address, a phone number, project and
reference codes, and a UUID \emph{canary}, \canary{}. None of these strings exists
anywhere on the public internet, so any occurrence in captured network traffic is
unambiguously attributable to our input. The canary in particular gives a single,
unforgeable yes/no signal: if it appears in outbound traffic, the confidential payload
provably reached the tool's servers.

\subsection{Interception setup}

All captures were performed on an isolated Kali Linux virtual machine so that the
man-in-the-middle configuration never touched real browsing. We used
mitmproxy~\citep{mitmproxy} (version 12.2.3) as an intercepting HTTPS/WebSocket proxy
on \texttt{127.0.0.1:8080}. Each tool ran in its own clean Firefox profile with the
proxy configured and the mitmproxy certificate authority trusted \emph{only within
that profile}, so decryption was scoped to the experiment. Before any data collection,
interception was verified per profile (a known HTTPS site must load without a
certificate warning and appear in the proxy); this guards against the most dangerous
failure mode in such studies, in which a broken interception silently looks identical
to a genuine zero-exposure result.

The document was pasted into a bare local HTML page containing a single text field and
nothing else (no third-party scripts, analytics, or other domains) served over
\texttt{http://localhost} so that extension content scripts activate exactly as they
would on a real site, but with zero background noise to filter out.

\subsection{Capture procedure}

For each run, the document was loaded into the clipboard and pasted with a
\emph{real, manual} \texttt{Ctrl+V} into the focused field, after which the run
recorded for sixty seconds. The manual paste is a deliberate methodological point: a
scripted/synthetic paste fills the field visually but does not fire the DOM
\texttt{input} event the extensions listen for, so the tool never ingests the text and
nothing is transmitted, a misleading ``clean'' zero. A genuine keystroke is what
causes the tool to receive the document. Each tool was captured for \textbf{five runs}
and the baseline for \textbf{three}, following an identical, locked protocol so that
between-run variance measures reproducibility rather than procedural drift.

\subsection{Metrics}
\label{sec:metrics}

A mitmproxy add-on scored every decrypted outbound request, response, and WebSocket
frame; the raw captures were also archived so they can be re-analysed offline. We
report, in order of importance:

\begin{description}[nosep,style=nextline]
  \item[Planted-secret count (headline).] How many of the twelve identifiers reached
        the servers, verified individually. The canary makes this unambiguous.
  \item[Exposure \%.] The fraction of the document's characters whose 20-character
        sliding window appears anywhere in outbound traffic, after subtracting hosts
        seen in the baseline:
        \begin{equation}
          \mathrm{Exposure}\,(\%) = \frac{\bigl|\{\, i : w_{20}(i) \in \mathcal{T} \,\}\bigr|}{N}\times 100,
        \end{equation}
        where $w_{20}(i)$ is the 20-character window starting at character position $i$,
        $N$ is the document length in characters, and $\mathcal{T}$ is the
        baseline-subtracted outbound traffic matched over all decoded variants.
        A 20-character window is long enough to avoid false
        matches from common words and short enough to catch fragmented sends; a
        per-host concatenated-transcript pass additionally catches content split
        across multiple frames. Matching is performed over plain, URL-decoded,
        JSON-unescaped, HTML-entity, base64-decoded, and UTF-16 variants so that encoded
        transmission is still detected, and compressed bodies (gzip, brotli, zstd) are
        decoded before matching.
  \item[Reproducibility.] The standard deviation of exposure \% across a tool's runs,
        labelled High ($<3$~pp), Medium ($3$--$10$~pp), or Low ($>10$~pp).
  \item[Traffic visibility.] Reported as \emph{two} separate numbers: the share of
        intercepted events that used HTTPS, and the count of TLS handshakes that could
        not be intercepted (e.g.\ certificate pinning), never combined into a single
        figure, because a non-zero failure count means the exposure result is a lower
        bound.
\end{description}

\noindent
We additionally report a 95\% confidence interval on the mean exposure using a
$t$-distribution ($n{-}1$ degrees of freedom), and use non-overlapping intervals as
informal evidence of a real difference between conditions.

\section{Results}
\label{sec:results}

\subsection{Headline: both tools transmit the whole document and every secret}

Table~\ref{tab:results} and Figure~\ref{fig:exposure} summarise the findings. Both
extensions transmitted essentially the entire document and \textbf{all twelve planted
secrets, including the canary}, to their servers. Grammarly transmitted a median
\textbf{99.0\%} of the document's characters; LanguageTool transmitted \textbf{91.9\%}.
The no-extension baseline transmitted \textbf{0.0\%} and none of the secrets. All
transmission used HTTPS, and there were \emph{zero} un-interceptable TLS handshakes, so the reported figures are complete, not lower bounds.

\subsection{Information types transmitted}
\label{sec:infotypes}

Grouping the twelve planted secrets by \emph{type} shows that the leak is not confined
to any single class of data. Both tools transmitted every information type present in
the document (personal names, contact details, official identification numbers,
financial codes, a legal contract reference, the confidential project codename, and the
unique canary), while the no-extension baseline transmitted none of them
(Figure~\ref{fig:infotypes}). Structured identifiers and regulated personal data are
therefore exfiltrated just as readily as free-text prose; nothing about being a formatted
ID number affords any protection.

\subsection{Beyond the planted secrets: a transmitted credential}

Grammarly's outbound WebSocket carries more than the user's document: travelling
alongside it is a \textbf{JSON Web Token} (an authentication credential, recognisable
from its \texttt{eyJ\ldots} encoding of a \texttt{\{"kid":\ldots\}} header) together
with opaque per-session client identifiers. The same channel that exfiltrates the
confidential text therefore also exposes the tool's own session credential.
LanguageTool's payloads contain no such artefact. We surfaced this by running an
automatic PII detector (Microsoft Presidio) over the decrypted bodies and manually
discarding its false positives (document dates, quarter labels, financial figures).
Because it is a manual-review result over the existing captures, we report it as an
indication rather than a quantified headline. The consequence widens the attack surface
beyond privacy: exposed session tokens and API keys are exactly what large-scale
credential-harvesting operations mine from client-side code and application
traffic~\citep{anthropic2026threats}. A writing assistant that emits its own session
credential alongside the user's text is therefore leaking a directly abusable secret, not
just personal data.

\subsection{Exact reproducibility}

Both tools produced \emph{identical} exposure on every run (standard deviation
0.0~percentage points), so we report this as a \emph{deterministic observation} rather
than a sampling estimate: the 95\% confidence intervals collapse to points (Grammarly
$[99.0,99.0]$, LanguageTool $[91.9,91.9]$) and carry no significance claim. Practically,
pasting the document causes the same near-complete transmission every time, consistent
with the upload being a fixed part of the tools' normal operation rather than an
occasional event.

\subsection{What was transmitted, and how}

Grammarly streamed the document to its backend over a WebSocket connection (a median
of roughly 6~kB of outbound payload per run across about two tool-related hosts).
LanguageTool sent it as an HTTPS \texttt{POST} to \texttt{api.languagetool.org/v2/check}
(roughly 5.6~kB to a single host). In both cases the twelve planted identifiers,
including the canary, were recovered from the decrypted outbound traffic. The
$\sim$8~percentage-point gap between the two tools reflects how much surrounding
boilerplate each includes rather than any difference in whether the sensitive content
leaves: both transmitted \emph{all} of the sensitive tokens.

Viewed over time (Figure~\ref{fig:timeline}), the transmission appears as a single
outbound burst at the moment the document is pasted, after which the connection falls
quiet. The no-extension baseline is instructive: it generates \emph{more} total traffic
than either tool run, megabytes of browser and OS background activity, yet none of
it carries document content. This is the same reason a baseline condition is required at
all: it isolates the environment's own chatter so that document-bearing traffic can be
attributed unambiguously to the installed tool rather than to the browser or operating
system.

\subsection{Independent corroboration without a proxy}

A natural objection to any man-in-the-middle measurement is whether the proxy itself
induced or altered the transmission. We addressed this with an independent capture that
removed the proxy entirely: Grammarly's browser profile was switched to a direct
connection, no interception of any kind, and the same document pasted while a
packet capture (\texttt{tcpdump}) recorded the machine's traffic, with encrypted-SNI
disabled so that destination host names remained visible. The capture showed the browser
resolving \texttt{assets.grammarly.com} and uploading several kilobytes directly to
Grammarly-owned infrastructure, an AWS EC2 backend
(\texttt{ec2-44-213-83-95.compute-1.\allowbreak amazonaws.com}) and three CloudFront edges
(\texttt{*.fra60.r.cloudfront.net}), within the paste window. The payload is opaque in
this mode (the browser build does not export TLS session keys, so direct traffic cannot be
decrypted without the proxy), but the destination and timing confirm that the upload occurs
with nothing intercepting it. The proxy is therefore an observation instrument, not the
cause of the transmission.

\subsection{Two exposure classes}

The excluded-tool investigation (Section~\ref{sec:limitations}) surfaced a distinction
worth stating as a result. Writing tools fall into two behavioural classes under this
threat model: \emph{automatic / background} transmitters, which send the document with
no user action beyond pasting (Grammarly and LanguageTool), and \emph{on-demand}
transmitters, which send only text the user actively submits (e.g.\ a paraphraser
invoked by selecting text and clicking ``rewrite''). Under the study's exact scenario (an extension running in the background while the user merely pastes), the
automatic class leaks and the on-demand class does not. Grammar checkers trend toward
the automatic class; paraphrasers toward the on-demand class. This is a meaningful
distinction for users and policy, not a measurement artefact.

\subsection{Background behaviour when idle}

To separate content transmission from mere background activity, we ran a twenty-minute
capture with the Grammarly extension loaded on the test page and \emph{no user action at
all}, no paste, no typing, no clicks. The capture path was confirmed live by the
presence of the browser's own background traffic (e.g.\ \texttt{ads.mozilla.org}) as a
positive control, without which a quiet result could not be distinguished from a broken
capture. Grammarly was not dormant: twenty-three of twenty-seven captured events reached
five Grammarly backend hosts: \texttt{auth.grammarly.com},
\texttt{config.extension.grammarly.com}, \texttt{gateway.grammarly.com},
\texttt{capi.grammarly.com}, and a logging endpoint \texttt{f-log-extension.grammarly.io}
(\texttt{POST /logv2}), consistent with authentication, configuration polling, session
upkeep, and telemetry. However, \textbf{none of this idle traffic carried
document content or any planted secret} (0\% exposure, 0 of 12). The extension thus
maintains a continuous background relationship with the vendor simply by being installed
and loaded, while the document itself leaves only once the user supplies text. Both facts
matter for the threat model: the tool is always connected, but content exposure is
input-triggered.

\subsection{Delivery channel: browser extension vs.\ desktop client}

A preliminary desktop probe reinforces that the exposure is a property of the
\emph{browser-extension} delivery rather than of grammar checking itself. LanguageTool's
official standalone desktop application (version~6.6, obtained from the vendor's own
site) was run through the identical interception setup and given the same document: it
performed the check entirely on-device and transmitted \textbf{nothing}, 0\% of the
document and 0 of 12 secrets, whereas the same vendor's browser extension transmitted
91.9\% and all twelve secrets to \texttt{api.languagetool.org}. The desktop client
exposes no option to use a remote server, so the on-device path is not merely available
but the only one. This is a single-run probe on one desktop client, reported as an
indication rather than a headline result; the fuller desktop and system-level study
follows in Section~\ref{sec:action-spectrum}.

\subsection{Desktop and system-level exposure: an action spectrum}
\label{sec:action-spectrum}

To test whether the browser-extension finding generalises, we repeated the
measurement on the host operating system (Windows~11) against desktop
applications and the everyday act of \emph{opening} a received file. The same
synthetic document and planted secrets were used, captured with the same
\texttt{mitmproxy} add-on; interception on the host required trusting the proxy
CA in the Windows store and routing traffic through a system proxy enabled only
during capture. The results arrange themselves along a spectrum of user action
(Figure~\ref{fig:action-spectrum}).

Figure~\ref{fig:action-spectrum} summarises every condition; the prose below highlights
only the findings that change the interpretation, naming each receiving host inline.

\paragraph{Active submission leaks, as in the browser phase.} The \textbf{DeepL} desktop
client, given the document by paste, transmitted essentially all of it (99.6\% mean over
three runs) and every secret to \texttt{www2.deepl.com}; the whole input was uploaded even
though the free tier only \emph{translates} the first 1500 characters. Invoking
\textbf{Edge's Copilot} to summarise the planted PDF transmitted \textbf{76.9\%} of the
file and all twelve secrets to \texttt{copilot.microsoft.com} (three runs, identical). The
coverage is lower than the paste-based tools not because less leaked but because the source
was a PDF: Edge transmits its \emph{text extraction} of the file, which drops layout and
formatting characters, yet every one of the twelve secrets, canary included, was sent. One
run is worth isolating: when asked instead for ``interesting facts,'' Copilot's visible
reply stated it would answer \emph{without} exposing the confidential details, yet the
capture shows the full document, canary included, had already been sent to Microsoft. A
model declining to \emph{display} a secret is therefore not evidence that the secret was
not \emph{transmitted}; the privacy boundary is the network, not the chat reply.

\paragraph{Merely opening a document in Word leaks it.} Opening the same document as a
\texttt{.docx}, with no paste and no submission, streamed \textbf{96.8\%} of it and every
secret to \texttt{augloop.svc.cloud.microsoft} (Microsoft's ``Augmentation Loop,'' the
cloud backend for Office's Editor/Copilot services, via posts to an
\texttt{OfficeCopilotOrchestrationWorkflow}), reproducibly across three runs. These
services are on by default in Microsoft~365 and Microsoft documents that its ``connected
experiences that analyse content'' process document text in the cloud, are enabled by
default, and can be disabled through an Office privacy setting, with an EU Data Boundary
and GDPR commitments for the processing~\citep{microsoft2026copilotprivacy}. The
exfiltration therefore came from the \emph{default productivity suite itself}, not an
add-in.

\paragraph{Disabling one setting stops it (causation and mitigation).} Turning off the
single Office setting ``experiences that analyse your content'' and reopening the same
file reduced augloop's transmission to \textbf{0\%} (0/12), with the socket still opening
but carrying no document content. This both establishes that the Office~AI feature, not
the act of opening a file, is the cause, and gives users a concrete one-switch mitigation.
It removes Microsoft's own channel only, however: a third-party assistant hooking the same
window is unaffected, as the Protected View result next shows.

\paragraph{Protected View does not stop a third-party assistant.} When the file carried a
mark-of-the-web and opened in Word's sandboxed \emph{Protected View} (the yellow ``Enable
Editing'' banner still showing, no user action), Microsoft's own augloop stayed silent,
Protected View contained it, but the \textbf{Grammarly} desktop client, hooking the text
at the accessibility layer, still transmitted \textbf{94.2\%} of the document and every
secret to \texttt{capi.grammarly.com}. Protected View thus sandboxes macros and even
Microsoft's own AI, but not an independent assistant reading the same window.

\paragraph{A file merely stored on a USB or cloud drive is not read by the tools.} A
distinct question is whether a confidential file leaks simply by being \emph{stored} on a
removable drive or a synced cloud folder while the writing assistants run in the
background. It does not. Inserting the USB without opening the file (only the Windows
indexer and shell probed volume metadata, per Process Monitor) and dropping the file into
iCloud~Drive to sync each transmitted \textbf{no} document content to the writing tools'
servers (0/12), even though
Grammarly and the other clients were running throughout: the file never entered a surface
they watch. iCloud's own content channels were reachable but carried no cleartext: the file
syncs to Apple encrypted in transit and, under Advanced Data Protection,
end-to-end~\citep{apple2024platformsec}, so it reaches Apple's cloud but is never exposed to
the LLM writing tools. The same held for opening the file in a viewer with no cloud-AI
integration (Notepad, Adobe~Acrobat, or Chrome's PDF viewer), and for opening the PDF in Edge
\emph{without} invoking Copilot (0/12; Edge-passive 1.8\% of incidental boilerplate).
Consumer antivirus (\textbf{Avast}) is a separate class rather than an LLM tool: it
uploaded an unknown \emph{executable} to its cloud (CyberCapture) plus reputation and
telemetry, but not the document's contents. Per-host attribution was essential throughout:
Grammarly, always running as a background actor, occasionally re-scanned the file and had
to be attributed away from the tool under test (e.g.\ in the antivirus run) rather than
mis-credited.

\paragraph{Interpretation.} Exposure is \emph{surface-dependent}, not
\emph{storage-dependent}: a file on a USB stick or in a synced cloud folder is not read by
the writing tools until its text enters a surface they watch, so passively receiving or
opening a file transmits nothing unless that surface has a cloud-AI integration watching
the content. Content leaves the machine whenever it enters such a surface, whether the user
pastes into a writing assistant, invokes an assistant, or merely opens the file in a
cloud-AI-enabled editor.

\subsection{Permissions: the channel is text, not the microphone}
\label{sec:permissions}

A natural question is whether these tools reach beyond text into device sensors. Auditing
the Windows capability store (mic, camera, location, contacts, full-disk access, and the
rest) and each extension's declared permissions showed that none of the writing or
translation tools (Grammarly, LanguageTool, DeepL, QuillBot) holds microphone, camera, or
broad-filesystem access: the microphone and camera belong only to communication, voice,
and meeting apps. What the writing tools do hold is the browser's ``read and change all
your data on all websites'' host permission, which is precisely the capability that lets a
content script read every editable field. The exposure channel is therefore the text a
user types or pastes, granted through an all-sites content permission, not audio or video
surveillance. Grammarly is instructive: its declared extension permissions look modest
(``read browsing history,'' ``display notifications''), yet it transmits 99\% of the
document, so declared permissions understate actual data access. Consistent with the
passive-leak results, the always-on writing clients (Grammarly, DeepL) are configured to
launch at start-up, so they are already watching before the user does anything.

\section{Discussion}
\label{sec:discussion}

The most telling single data point is not the percentage but the canary. A unique
token that existed only inside a document marked ``\textsc{do not forward}'' was found,
seconds after an ordinary paste, in traffic bound for two companies' servers, placed
there by software the user installed once and forgot. Nothing here is a bug or an
exploit: server-side analysis \emph{requires} the text to be uploaded, and both vendors
document that they process user text. The finding is about the distance between that
design and what a user, told ``don't share this with AI,'' would reasonably believe had
happened when they simply pasted a paragraph into an unrelated field.

This distance matters because the exposure is (a) invisible: there is no prompt, no
click, no confirmation; (b) complete: essentially the whole document, not a
fragment; and (c) deterministic: it happens every time, reliably. For an individual
handling regulated data (health, legal, financial) the implication is direct:
default-configuration writing assistants are incompatible with a ``do not share''
instruction unless explicitly disabled, and disabling them is not the default. The
two-class distinction gives users a practical lever: automatic grammar checkers are the
ones that leak passively, whereas on-demand paraphrasers only transmit what is actively
submitted.

\paragraph{Regulatory implications (EU/GDPR and Germany).} Because the memo contains
personal data---names and an employee identifier---the behaviour we measure engages the
EU General Data Protection Regulation (GDPR, Regulation (EU)~2016/679). A silent,
whole-document upload sits in tension with several of its principles: lawfulness and
transparency (Art.~5(1)(a), 6), as the transfer is neither disclosed to the user nor
obviously grounded in a legal basis; data minimisation (Art.~5(1)(c)), as the entire
document is sent rather than the text under review; and the information duties of
Arts.~13--14, as the user is never told the text leaves the device. Where the receiving
servers sit outside the EU, the transfer additionally engages the Chapter~V safeguards
(Arts.~44--49). The gap is sharpest in an organisational setting: an employer whose staff
paste client data into a consumer writing assistant with no Art.~28 processor agreement is
the realistic non-compliance scenario, and in Germany the analysis is stricter still,
layering the Federal Data Protection Act (BDSG) and works-council co-determination over
tools that can observe employee input. This does not render every use unlawful: Microsoft,
for one, documents an EU Data Boundary and a processor agreement for Office's cloud
processing~\citep{microsoft2026copilotprivacy}, so the same feature can be deployed
compliantly. The distinction our results draw is thus practical---between vendors that
offer a lawful-processing path and default-on consumer tools that offer none---which makes
the \emph{invisibility} of the transfer, not merely its occurrence, the core
data-protection concern. We offer no legal determination; establishing a violation is
fact-specific and beyond a measurement study.

\section{Limitations and Excluded Tools}
\label{sec:limitations}

\paragraph{Excluded tools (the honest trail).} Not every candidate fit the controlled
Firefox method, and recording why is part of the methodology.
\begin{itemize}[nosep]
  \item \textbf{ProWritingAid}: a genuine extension, but it did not attach to the
        controlled test field (it sent only small heartbeats, never the document), so
        it produced no measurable transmission under this protocol.
  \item \textbf{QuillBot}: has no official Firefox extension (Chrome only) and so
        cannot be tested under a Firefox-based method that must be identical for every
        tool.
  \item \textbf{Wordtune}: the obvious Firefox listing proved to be a
        \emph{counterfeit} (a clone under an unrelated publisher, with a scam support
        link, that echoed text locally and never contacted a server); the genuine tool
        is published by AI21 Labs but is \emph{on-demand} and therefore does not leak
        on a background paste. This points to a practical user lesson: verify an
        extension's publisher before installing.
\end{itemize}

\paragraph{Other limitations.}
\begin{itemize}[nosep]
  \item \textbf{Single document.} All runs used one test document. The supervisor-agreed
        design called for three (a memo, a longer report, and a code snippet); only the
        memo was measured. Because the finding is essentially ``all of it, every time,''
        document-to-document variance is unlikely to change the qualitative result, but
        the two additional documents remain unmeasured and are noted as an open item.
  \item \textbf{Controlled field.} A bare local page isolates the signal but is not a
        real website; a small number of Gmail/Google-Docs confirmation runs would test
        representativeness (planned as future work).
  \item \textbf{Cloud-sync coverage.} Of the consumer cloud-sync clients, only iCloud
        Drive was measured (no cleartext content observed); a dedicated OneDrive
        drop-and-sync run was not performed and is left as future work.
  \item \textbf{Tool drift.} These are cloud products that auto-update, and prior
        longitudinal work shows extension/app privacy behaviour shifts across versions
        \citep{ren2018piileaks}. The \emph{pipeline} reproduces exactly; the specific
        percentages reflect tool behaviour at capture time (each run is timestamped).
  \item \textbf{Scope of interception.} Certificate pinning can hide traffic; here the
        count of un-interceptable handshakes was zero, so this did not affect the
        result, but in general the exposure figure is a lower bound. TLS interception
        can itself alter or weaken the connection it observes~\citep{durumeric2017https};
        our proxy CA is trusted only in the isolated test profile, and we report the
        raw exposure without relying on any modification of the traffic.
  \item \textbf{Two environments, not exhaustive.} The browser phase used Firefox on a
        controlled Linux VM; the host phase used Windows~11 with desktop clients and
        Office. Other browsers (Chrome/Edge as the \emph{primary} profile) and other
        operating systems (macOS) were not covered and could differ.
  \item \textbf{Manual trigger timing.} The paste that triggers transmission was
        performed by hand, so the absolute time of the transmission varies between runs.
        This affects only \emph{when} the spike occurs, not \emph{whether} it does, nor
        the measured exposure.
  \item \textbf{Unequal run counts.} Five runs per tool and three baseline runs. Because
        every run of a given condition was identical (zero variance), additional runs
        would not change the reported values, but the asymmetry is noted for
        completeness.
  \item \textbf{Detection method.} Sensitive tokens are detected by case-insensitive
        substring match and document coverage by a 20-character sliding window. Because
        the planted identifiers are long and synthetically unique, the risk of a
        coincidental (false-positive) match in unrelated traffic is negligible; the
        20-character window likewise avoids matches on common short strings.
\end{itemize}

\paragraph{Host-phase caveats.}
\begin{itemize}[nosep]
  \item \textbf{Certificate pinning (lower bound).} Several native Windows and
        vendor channels (e.g.\ \texttt{*.events.data.microsoft.com}, some Adobe
        and Google endpoints) refused interception, so their payloads are opaque.
        Reported host-phase exposure is therefore a lower bound: only decryptable
        traffic is counted.
  \item \textbf{Single machine and configuration.} Host runs used one Windows~11
        laptop signed into one Microsoft~365 account with Office AI features at
        their defaults; the USB was a card-reader drive. The Word/Office result is
        contingent on that default-on configuration and would not occur with
        intelligent services disabled or an offline account.
  \item \textbf{Opaque uploads not size-profiled.} We count only content we can
        decrypt and string-match; a compressed or binary payload to a pinned host
        could in principle carry document data we cannot see. We flag every pinned
        host and treat host figures as lower bounds, but did not add an
        outbound-byte-volume anomaly detector to bound that residual.
  \item \textbf{Native desktop clients (system-proxy blind spot).} The system proxy
        captures only traffic that honours it, which browser extensions and Office both
        do. A native client may use its own sockets: the Grammarly Windows client attached
        to Notepad sent only telemetry over the proxied channels (no document content, 0/12),
        yet a per-process audit found it also holding a direct TLS socket to an AWS endpoint
        that bypassed the proxy, whose payload we could not inspect. We therefore report
        Notepad-with-a-desktop-assistant as \emph{unmeasured}, not zero; full interception of
        such clients needs a transparent (WinDivert) proxy or a Frida hook (future work).
        Proxy-captured results---browser extensions, Office/augloop, and Grammarly-in-Word
        via \texttt{capi}---are unaffected.
  \item \textbf{Background-actor confound.} Other assistants (notably the Grammarly
        desktop client) ran throughout the host phase, as on a real machine. Per-host
        attribution separated their traffic from the tool under test in every case
        (e.g.\ the antivirus run), but a fully clean-room host with no other assistant
        installed was not used.
\end{itemize}

\section{Ethics and Responsible Disclosure}

All test data is synthetic: no real person, organisation, or system is referenced, and
no real personal data was captured or transmitted. The study measures
default-configuration behaviour of legitimately installed software on the researcher's
own machine; it does not attack the vendors' systems or other users. Consistent with
responsible-disclosure norms, findings are intended to be shared with the affected
vendors, with a reasonable window to respond, before any public release of the
repository.

\section{Conclusion and Future Work}

Two independent, widely used grammar-checking browser extensions each silently
transmitted essentially an entire confidential document, and every one of twelve
planted secrets, including a unique canary, to their servers, automatically, on a
single paste, with exact reproducibility, while a no-extension baseline transmitted
nothing. The tools are behaving as designed; the result documents how far that design
sits from the expectations of a user told not to share a document with AI tools, and it
distinguishes the automatic transmitters that leak passively from on-demand tools that
do not. Moving beyond the browser to \emph{desktop and system-level} exposure
(Section~\ref{sec:action-spectrum}) showed the leakage is not unique to browser
extensions: the DeepL desktop client, an invoked Edge/Copilot summary, and simply
\emph{opening} a document in Microsoft~Word each transmit essentially the whole document
by default, whereas passive receipt (USB, iCloud sync) and non-AI viewers do not.
Disabling a single Office setting removes the Word leak, confirming the cause and giving a
concrete mitigation, and a permission audit shows the channel is all-sites text access,
not device sensors. The unifying lesson is that exposure is surface-dependent: content
leaves the machine whenever it enters a surface an LLM-integrated service monitors, rather
than being tied to any single application.

\paragraph{Future work.} The main remaining gaps are breadth rather than new mechanisms:
real-field confirmation runs (Gmail, Google~Docs); the two further documents from the
intended three-document set (a longer report and a code snippet); a primary-browser
(Chrome/Edge) and macOS environment; a dedicated OneDrive drop-and-sync run; and
additional captures to raise the remaining single-run host probes to the reproducibility
already achieved for the Word, DeepL, and Edge/Copilot conditions. Two mechanistic
extensions stay open: dynamic instrumentation (e.g.\ Frida) to see inside
certificate-pinned channels that are currently only a lower bound, and an outbound-volume
detector to bound opaque uploads. The automated PII sweep with Microsoft
Presidio~\citep{microsoft2018presidio}, already used here to surface an unplanted session
credential, can be broadened into a full per-category inventory of unplanted personal
data across the captures.
